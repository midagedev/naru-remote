# Contributing to Naru Remote

Thanks for being here. This document is short on ceremony and specific about the
two or three things that actually matter in this codebase.

## The fastest useful contribution

**A good bug report.** Naru talks to real VNC servers over real networks, and
the failures that matter are the ones no fixture predicted. If something
misbehaves:

1. In the app, open **Session tools → Diagnostics** and tap **Share**.
2. Paste that export into the issue.

The export is designed to be safe in public: it carries stage results from a
fixed catalogue — DNS, TCP, RFB handshake, auth, first frame — and never
addresses, passwords, screen contents, or text you composed. If you want to know
exactly what it contains before you post it, read it; it is plain text.

## Before you open a pull request

### 1. Behaviour changes need a spec

This repository is developed spec-first. Anything that changes what the app
*does* — not a typo, not a refactor — starts as a directory under `specs/`:

```
specs/<n>-<slug>/spec.md
```

The spec states what was observed, why it is wrong, what "fixed" means, and how
that will be verified. It is not paperwork; the specs are the reasoning record
of the project and they stay in the repository afterwards. Read a recent one —
`specs/038-session-ux-punchlist/spec.md` is a representative example — before
writing your first.

If you are unsure whether your change needs one, open an issue and ask. A
mislabelled bug fix is not a problem; an undocumented behaviour change is.

### 2. Compiling is not done

Every behavioural change lands with a test that **fails without it**. Please
confirm that yourself: revert your fix, watch the new test go red, restore it.
A test written after a fix that was never seen failing is a test that might be
asserting nothing.

Where an existing test *should* have caught the bug and didn't, say so in the
spec and explain why it couldn't. That note is usually worth more than the fix,
because it tells the next person which shape of defect the suite is blind to.

### 3. Run the gates

```bash
swift build && swift test          # core + app model + fake RFB server
xcodegen generate --spec project.yml
xcodebuild -project NaruRemote.xcodeproj -scheme NaruRemote \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=26.2' test
```

Some UI gates skip themselves when the environment cannot produce the outcome
under test — a Korean keyboard for the hostname-field gate, PiP support that no
simulator has. A skip with a reason is a correct result. A skip that hides a
real failure is not, so keep them narrow.

## Things that will come up in review

These are the rules this codebase enforces, drawn from
`.specify/memory/constitution.md`:

- **Input is composed locally.** Remote key events are a compatibility fallback,
  never the primary path for multilingual text. If you add an input feature, name
  its injection adapter and say what happens when the remote app blocks it.
- **Credentials live in the Keychain**, referenced by name. Never on
  `ConnectionProfile`, never in the profile file.
- **Logs keep counts, not content.** No coordinates, no byte counts, no
  framebuffer dimensions, no user text in logs, diagnostic exports, or test
  assertions. Diagnostic strings come from a fixed catalogue, not from raw
  errors.
- **Private-network first.** No public-internet-first UX, and no language
  implying affiliation with or replacement of Tailscale.
- **iPhone before iPad.** The verification matrix lists an iPhone path first.
  iPad-only affordances are enhancements, not gates.
- **Prove protocol behaviour.** For RFB or clipboard work, demonstrate it against
  the `FakeRFBServer` fixtures rather than against the specification — real
  servers routinely disagree with the spec, and this project has the scars.
- **`NaruRemoteCore` imports no UI framework.** No SwiftUI, no UIKit. That
  boundary is what keeps the test loop fast.

## Layout

```
NaruRemote/Sources/NaruRemoteCore/   pure logic — no SwiftUI, no UIKit
NaruRemote/App/                      SwiftUI shell + app model
NaruRemote/iOSApp/                   app entry, concrete stores
NaruRemote/Tests/                    swift test targets
NaruRemote/UITests/                  XCUITest
TestFixtures/FakeRFBServer/          deterministic protocol fixtures
specs/                               one directory per behaviour change
```

`NaruRemote.xcodeproj` is generated by XcodeGen from `project.yml`. Don't edit it
by hand; regenerate.
