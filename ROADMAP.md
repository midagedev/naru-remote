# Roadmap: Naru Remote

Updated: 2026-04-30 KST

## Current Position

Naru Remote is in the MVP vertical-slice stage. The product direction, brand,
Spec Kit workflow, core Swift package, generated Xcode app target, first
SwiftUI app shell, fake RFB server, and initial production RFB boundary
integration are in place.

Current executable targets:

- `NaruRemoteCore`: profile, diagnostics, onboarding, compose, text injection,
  session, and RFB protocol boundary logic, plus initial PiP Watch Mode state.
- `NaruRemoteApp`: SwiftUI shell for onboarding, profiles, session viewport,
  Remote Input Dock, and diagnostics summary.
- `NaruRemote`: installable iOS/iPadOS app bundle generated by XcodeGen.
- `NaruRemoteUITests`: iPad simulator launch verification.
- `FakeRFBServer`: deterministic TCP fixture server for RFB 3.8 no-auth,
  raw-frame, and VNC password authentication testing.

Current verification:

- `swift build`
- `swift test` with XCTest coverage for core, app shell, fake RFB, onboarding,
  PiP watch state/profile policy, diagnostic export safe catalog behavior, and
  app-shell profile/add/connect/send coordination, file-backed profile
  persistence, raw framebuffer decoding, and repeated raw framebuffer update
  requests over one active no-auth connection, cancellable frame pump behavior,
  incremental raw update compositing with dirty-region/change metadata,
  long-lived app frame streaming with profile-change cancellation, and first
  framebuffer storage in the app model, plus VNC password challenge-response,
  authenticated fake-server sessions, credentialRef-only profile password
  storage, Keychain-backed app credential lookup, and app-level PiP Watch
  start/stop/staleness lifecycle, sample-buffer renderer coverage, and
  app-model system PiP controller wiring
- `xcodegen generate --spec project.yml`
- `xcodebuild -project NaruRemote.xcodeproj -scheme NaruRemote -destination 'platform=iOS Simulator,name=iPad Pro 13-inch (M5),OS=26.2' build`

## Phase 3 - Deterministic RFB Integration

Status: complete for repeated raw-frame, VNC password-auth, and app credential
lookup primitives

- Build a networked fake RFB server executable from the existing transcript
- Add client integration tests against the fake server
- Initial no-auth first-frame transcript path is verified over TCP
- Interactive no-auth first-frame handshake is verified over TCP with client
  version/security/ClientInit/framebuffer-update-request writes
- Outgoing RFB `ClientCutText` and paste key-event writes are verified over the
  active fake-server connection
- 32-bit true-color raw framebuffer rectangles can be decoded into RGBA pixels
  in the core module
- `RFBNetworkClient` can keep a no-auth session open and request repeated raw
  framebuffer updates on the same connection against the fake server
- `RFBNetworkClient` can negotiate `VNC Authentication` security type 2 when a
  password is supplied, generate the VNC challenge response, and surface
  missing-password or rejected-password failures without stale session state
- Profile creation can capture an optional VNC password, store it through the
  credential store, persist only a `credentialRef` in profile metadata, and
  resolve that credential before authenticated streaming connections
- `RFBFramePump` provides a cancellable loop boundary: first full-frame request,
  later incremental requests, callback stop, cancellation, and error
  propagation are covered
- Incremental raw updates are composited onto the previous framebuffer, and
  dirty rectangles, changed pixel counts, and change activity are preserved for
  future Metal texture upload and PiP FPS policy decisions
- The app model runs a long-lived frame task for streaming-capable connectors,
  updates `latestFramebuffer` as later frames arrive, cancels stale streams on
  profile changes, and the session viewport can show a sampled SwiftUI
  framebuffer preview
- `RFBNetworkClient` updates production boundary state from the fake server
- Failed reconnects clear stale frame metadata, and short transcripts return a
  typed error instead of trapping
- Current boundary does not yet render full-rate pixels with SwiftUI/Metal,
  restore remote clipboard contents, emit broader pointer/keyboard events, or
  verify saved credentials against real VNC servers on physical devices
- Next: add clipboard text message fixtures, SwiftUI/Metal frame presentation,
  and real-server credential verification
- Keep real-server compatibility claims blocked until this phase passes

## Phase 4 - VNC Client Implementation Choice

Status: selected for MVP

- Use first-party Swift RFB boundary/minimal client subset for the MVP
- Keep RoyalVNC as the preferred post-MVP candidate after build integration,
  Unicode clipboard, auth, and iOS framebuffer behavior are verified
- Do not use LibVNCClient for the iOS MVP because GPL-2.0 and C bridge costs
  are too high for this stage

## Phase 6 - PiP Watch Mode

Status: started

- Product contract: watch-only remote monitor, not interactive mini desktop
- Core state model and input-disabled watch policy
- Profile-level PiP opt-out with legacy profile defaulting
- PiP availability gated on an allowed session state and an already received
  remote frame
- Adaptive low-FPS frame policy for idle/moderate/high remote changes
- App shell "PiP Watch" action starts the core watch lifecycle when a selected
  session has a renderable frame; stale refresh and stop are model-backed
- Frame change activity now comes from the RFB update pipeline instead of a
  fixed incremental/full-frame heuristic
- App-layer renderer boundary converts `RFBRawFramebuffer` into BGRA
  `CVPixelBuffer` / `CMSampleBuffer`, enqueues frames on
  `AVSampleBufferDisplayLayer`, and compiles an iOS
  `AVPictureInPictureController` content-source wrapper
- Next: wire the wrapper into the app session surface and verify real
  iPhone/iPad PiP behavior, return-to-app behavior, and background-mode policy
- Next: system PiP renderer and profile settings UI for the opt-out

## Phase 10 - SSH And Terminal Mode (Aspirational)

Status: not started; explicitly out of MVP scope (`spec.md` Non-Goals)

This is the second product mode beyond VNC viewing. It is documented here so
the architecture's adapter boundaries (input bridge, profile, diagnostics,
credential ref) can stay open to it, not as a committed deliverable.

Direction:

- SSH session as a peer connection mode to VNC, sharing `ConnectionProfile`,
  `ConnectionDiagnostics`, and `ConnectionCredentialStore` boundaries while
  introducing a separate session/renderer pair (terminal stream, not
  framebuffer)
- Compose & Send remains the default multilingual input path (terminal-safe
  paste / bracketed paste); Direct Keystroke Streaming Mode from Phase 9 is
  the natural fit for live shell input
- Direct **tmux attach** as a higher-level convenience: connect with
  `ssh -t user@host tmux new -A -s naru` (or user-configured target session)
  so reconnection drops the user back into the same persistent terminal
  state. Treated as a per-profile option, not the only SSH path.

Open questions a future spec must close:

- Terminal emulation scope (xterm-256color baseline? scrollback policy? bell?
  OSC 52 clipboard?)
- Trust boundary for SSH keys, agent forwarding, known_hosts, and how the
  Keychain credential boundary extends to passphrases / private keys
- Multi-session coordinator implications (shared with Phase 8)
- Whether tmux attach is a first-class mode with its own diagnostic stage
  ("tmux session reachable") or just a saved post-connect command

Pre-spec gates: MVP physical-device verification complete; Phase 9 Direct
Keystroke Streaming Mode shipped (so terminals already have a working live
input adapter); Phase 8 multi-session coordinator scoped (so SSH can be a
session type rather than replacing the single-session app model).
